# 验收对照表（第五轮评审清单 → 实现位置 → 测试）

## P1：锁正确性（第五轮，只动 src/locks.py）

**互斥机制**：操作系统内核文件区域锁 —— Windows `msvcrt.locking`（LockFile 语义）、
POSIX `fcntl.flock`，非阻塞模式。"实例唯一有效持有者" = 唯一成功对
`LOCK_OFFSET`（内容区外 1MiB）处 1 字节区域加锁的文件句柄。

**为什么同一时刻最多一个有效持有者**（评审要求 6）：
1. 加锁由内核原子裁决：第二个进程对同一区域的加锁请求必然失败，
   不存在"检查→动作"窗口，因此**不需要接管操作，也就不存在接管竞态**（要求 1）；
2. 锁生命周期与句柄绑定：持有进程崩溃/被杀时内核自动回收——无"残留锁"状态，
   恢复动作本身就是一次原子加锁，天然并发安全（要求 3）；
3. 解锁/关闭只作用于本句柄持有的区域，内核拒绝释放非本句柄的锁——
   任何代码路径（包括 bug）都不可能释放别人的锁；
4. 锁文件永不 unlink（仅作汇合点+诊断载体）——不存在"旧持有者释放时
   删除新持有者文件"的路径（要求 2 的结构性保障）。

**实例唯一 token**（要求 2）：`acquire()` 生成 uuid4 写入诊断区；
`release()` 释放前核验文件记录 token 是否属于本实例（误用告警）。
注意：token 是身份标识与误用检测，不是互斥依据——互斥由内核语义保证。

**长任务保护**（要求 5）：本机制没有锁龄概念，活进程持锁任意时长均受内核保护。

**测试证据**（`tests/test_locks.py`，15 项，全部真多进程子进程，结果落盘防抖）：
- `test_concurrent_race_single_winner` —— 6 进程同时启动，恰好 1 个胜出；
- `test_concurrent_takeover_of_dead_residue` —— 硬杀制造死进程残留后 6 进程同时接管，恰好 1 个胜出（要求 4）；
- `test_race_on_corrupt_lock_file` —— 半截 JSON 残留上并发恢复，1 个胜出且信息被覆写合法（要求 3/4）；
- `test_incomplete_lock_file_recoverable[空/坏JSON/二进制]` —— 单实例可恢复（要求 3）；
- `test_stale_holder_release_cannot_remove_new_holders_lock` —— 旧持有者重复释放后，新持有者锁仍有效、文件未被删除（要求 4）；
- `test_long_task_holder_never_taken_over` —— 3 秒长任务窗口内 3 次尝试均被拒，释放后立即可获取（要求 5）；
- `test_alive_holder_rejected_and_crash_recoverable`、`test_mutual_exclusion_under_contention`（持锁窗口两两不重叠）等既有用例保留（要求 4/5）。

全套 **103 项测试通过**（约 23s，Windows 本机；CI 双平台矩阵自动运行）。

## P1：残留锁并发接管竞态 ✅（第四轮）

- **方案变更而非打补丁**（评审明确不建议 sleep/延长过期时间）：`src/locks.py`
  彻底移除"改名隔离 + 重建"的接管动作，改用操作系统自带文件区域锁——
  Windows `msvcrt.locking` / POSIX `fcntl.flock`（均为内核原子操作）。
  - 同一时刻最多一个进程持锁：内核保证，与重试/超时/锁龄参数无关；

  - Windows 细节：区域锁会拒绝其他句柄读取被锁字节，故锁区放在距内容
    1MiB 的高偏移处，持有人诊断信息（文件头部 pid/host/started）始终可读。
